# RE:年モノ MVP 設計

## 目的

毎年繰り返す仕事を、担当者個人の記憶ではなく Google Drive 上のファイル活動から再発見する。

MVPでは「例年モノそのものを完全自動判定する」ことより、次の仮説検証を優先する。

> Drive Activity API の過去履歴だけで、昨年同時期に活発だったファイルを現在の担当者へ再提示できるか。

## データフロー

```text
Google Drive
   │
   │ Drive Activity API / EDIT
   ▼
昨年同時期 ±21日 ──┐
                    ├─ ファイルID単位で集計
直近90日 ──────────┘
                    │
                    ▼
              候補フィルタ
                    │
                    ▼
                ランキング
                    │
                    ▼
        RE:年モノ - おすすめ（Sheets）
```

## なぜ「人」ではなく「ファイル」を主語にするか

人事異動がある組織では、昨年の担当者の個人履歴を今年の担当者へ引き継ぐ設計は壊れやすい。

一方、業務ファイルそのものが残っているなら、File ID をキーにすることで担当者の変更をまたいで季節性を捉えられる。

## MVP判定

### 昨年同時期

実行日の1年前を中心に ±21日。

次のどちらかを満たせば「昨年は活発」とする。

- 2日以上にわたって EDIT activity が存在
- EDIT activity が3件以上

同日に大量編集された一時的な作業も拾えるよう、活動日数と件数をOR条件にしている。

### 最近

直近90日に1日でも EDIT activity があれば推薦から除外する。

MVPでは「すでに今年の仕事が始まっているもの」を出さないことを優先する。

## スコア

```text
score = 昨年の活動日数 × 100
      + min(昨年のEDIT activity件数, 50) × 5
```

説明可能性を優先した暫定スコア。

活動日数を強く評価し、同一日に大量編集されたファイルだけが上位を独占しないようにする。

## 今年の目安

昨年の最初の activity 日を1年ずらし、

- あとN日くらい
- 昨年は今日ごろ開始
- 昨年はN日前ごろ開始

として表示する。

## 最重要の技術検証

Drive Activity API は過去アクティビティを問い合わせられるが、長期保持期間が明示保証されていない。

そのため `diagnoseHistory()` で約1年前の±30日を問い合わせる。

### 成功判定

- 約1年前の activity が複数取得できる
- 当時確実に使った既知のファイルが含まれる
- 他ユーザーが編集した共有ファイルも、期待する範囲で取得できる

### 失敗時

0件というだけでは保持期間不足とは断定しない。既知ファイルの履歴と照合する。

本当に長期履歴が取得できない場合は次を検討する。

1. Admin Reports API（利用権限・ログ保持期間を確認）
2. 今後の activity を日次で自前蓄積
3. Drive の revision / modifiedTime など弱いシグナルとの組み合わせ

## MVPでやらないこと

- AI / LLMによる内容理解
- ファイル本文の解析
- 個人ごとの嗜好学習
- 2年以上を使った周期性判定
- Google Chat / Gmailへの自動通知
- 自動で業務名をクラスタリング

まず「去年の活動履歴から役に立つ候補が出るか」を検証してから追加する。

## 次段階の Seasonal Frecency 案

2〜3年前まで取得できる場合は、単純な昨年スコアから周期性スコアへ進化させる。

```text
Seasonality =
    1.0 × 昨年同時期の活動
  + 0.7 × 2年前同時期の活動
  + 0.5 × 3年前同時期の活動

Score = Seasonality
      × 休眠度
      × 年ごとの再現性
```

毎年ほぼ同じ時期に活動が始まるファイルほど「例年モノ度」を高くする。
