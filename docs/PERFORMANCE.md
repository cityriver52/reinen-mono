# Performance

## 現在の取得戦略

Re:年モノは、対象フォルダ配下の昨年度1年分のDrive Activityを毎回総なめしない。

### Phase A: 季節ウィンドウだけ広く取得

対象フォルダごとに、1年前の今日を中心とする `±SEASONAL_WINDOW_DAYS`（デフォルト±21日、通常43日）の `EDIT` activityだけを取得する。

ここで次の最低活動量を満たしたファイルだけを候補にする。

- `MIN_SEASONAL_ACTIVE_DAYS` 以上の活動日
- または `MIN_SEASONAL_EDIT_ACTIVITIES` 以上のEDIT activity

### Phase B: 候補ファイルだけ年度背景を取得

Phase Aで候補になったFile IDについてのみ、Drive Activity APIの `itemName=items/FILE_ID` を使って比較年度（4/1〜翌3/31）全体を照会する。

季節ウィンドウのactivityはPhase Aですでに集計済みなので、Phase Bでは季節ウィンドウ内のactivityを無視し、年度内その他期間だけを加算する。

旧実装では「季節窓より前」「季節窓より後」を別々に照会していたため、候補1件につき原則2リクエスト必要だった。現在は年度全体を1回照会するため、候補別の初回リクエスト数をほぼ半減している。

```text
対象フォルダ
    ↓
今頃43日だけ検索
    ↓
季節候補 30ファイル
    ↓
30ファイル × 年度全体1照会
    ↓
季節窓を除外して背景集計
    ↓
seasonal_lift計算
```

## Drive Activity API のレート制御

実環境では `activity.query` に `Query Requests per minute per user = 100` の上限が適用されている。

`fetchAll()` で候補を無制限に並列化すると429 `RESOURCE_EXHAUSTED` になるため、次の制御を行う。

- 並列バッチは最大8件
- 1実行内の安全上限を80 queries/分とする
- Phase AとPhase Bで同じ60秒ローリング窓のリクエスト履歴を共有する
- 80件/分を超えそうな場合は `Utilities.sleep()` で自動待機する
- 429および5xxは指数バックオフして再試行する
- 候補別照会は最大4回まで再試行する

100件/分ぎりぎりまで使わず20%の余裕を取ることで、ページングや短時間の揺らぎを吸収する。

## 精度

候補判定の意味は変更しない。

- 比較単位: 年度（4/1〜翌3/31）
- 季節ウィンドウ: 1年前の今日±21日（デフォルト）
- `seasonal_lift`: 季節ウィンドウの活動日密度 / 年度内その他期間の活動日密度

取得順序とAPI呼び出し方法だけを変えている。

## 計測

`runReinenMono()` と `diagnoseHistory()` の戻り値に `elapsedSeconds` を含める。

実行ログには次も出力する。

- 季節ウィンドウで見つかったファイル数
- 年度背景まで調べる候補ファイル数
- 季節ウィンドウ検索の経過秒数
- seasonality query全体の経過秒数
- レート制御による待機時間
- 429/5xxの再試行

## まだ重い場合

次に最も効果が大きい改善は、**年度背景の永続キャッシュ**。

昨年度の「季節窓以外」の活動は過去データなので、同じFile ID・比較年度について毎週取り直す必要性は低い。候補別背景集計をCacheシート等へ保持すれば、週次実行では新しく候補になったファイルだけDrive Activity APIへ問い合わせる構成にできる。

その他の候補:

1. 季節ウィンドウ43日だけでもActivity量が非常に多い巨大フォルダ
2. 季節候補ファイル自体が数百〜数千件になるケース
3. 上位候補の `folder_path` 解決（Drive APIで親階層を辿る処理）
